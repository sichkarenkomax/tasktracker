# Модульная платформа управления работой

**Версия:** 0.1
**Статус:** разработка (Milestone 1 достигнут)
**Первый целевой релиз:** Core + Tasks
**Архитектурный подход:** Modular Monolith
**Backend:** Python / FastAPI
**Frontend:** React / TypeScript
**Database:** PostgreSQL
**Deployment:** Docker Compose

> Этот документ — проектное решение: что система собой представляет и почему
> именно так. Что сделано прямо сейчас, в какой задаче и что дальше — рабочий
> план [`roadmap.md`](roadmap.md) и [`README.md`](../README.md). Там же счётчики,
> которые здесь меняются каждую неделю; здесь — правила, которые меняться не
> должны.

## 1. Назначение проекта

Разработать лёгкую self-hosted платформу для управления рабочими процессами небольших и средних команд.

Платформа должна объединять базовые функции:

* пользователи;
* организации и команды;
* проекты;
* задачи;
* комментарии;
* уведомления;
* файлы;
* активности;
* права доступа;
* дополнительные модули.

Главный архитектурный принцип:

> **Платформа состоит из Core и независимых функциональных модулей.**

Core предоставляет фундаментальные сущности и сервисы.

Модули реализуют прикладную функциональность.

В дальнейшем к платформе должны без изменения фундаментальной архитектуры добавляться:

* Kanban;
* Gantt;
* Scrum;
* Chat;
* Calendar;
* Time Tracking;
* Wiki;
* Documents;
* CRM;
* AI;
* интеграции;
* Automation.

## 2. Основные цели

### 2.1. Простота

Система должна быть значительно проще в установке и сопровождении, чем крупные self-hosted платформы.

Базовая установка должна требовать минимальное количество компонентов.

Целевой первоначальный состав:

```text
Internet / LAN
      │
      ▼
   Caddy
      │
      ▼
   Backend
      │
      ▼
 PostgreSQL
```

Redis, очереди, отдельные workers, search engine и другие инфраструктурные компоненты не должны быть обязательными на первом этапе.

---

## 3. Основные архитектурные принципы

### 3.1. Modular Monolith

На первом этапе все модули работают внутри одного приложения.

```text
                    Platform
                       │
        ┌──────────────┴──────────────┐
        │                             │
       Core                         Modules
        │                             │
        │                ┌─────────────┼─────────────┐
        │                │             │             │
        │              Tasks        Kanban         CRM
        │
        └────────────── PostgreSQL
```

Модуль ≠ микросервис.

Модуль является логически изолированной частью приложения.

---

## 4. Почему не микросервисы

На первом этапе микросервисная архитектура запрещается.

Не требуется:

* отдельный контейнер для каждого модуля;
* отдельная БД для каждого модуля;
* Kafka;
* Kubernetes;
* service mesh;
* API gateway между внутренними модулями.

Это создаёт инфраструктурную сложность раньше времени.

Вместо этого используются строгие программные границы:

```text
Module A
   │
   │ public service/API
   ▼
Module B
```

а не:

```text
Module A
   │
   └── SQL напрямую
          │
          ▼
      Module B tables
```

---

## 5. Возможность будущего выделения модулей

Архитектура должна позволять в будущем вынести отдельный модуль в самостоятельный сервис.

Например:

```text
Platform
│
├── Core
├── Tasks
├── CRM
└── Chat
```

в дальнейшем может превратиться в:

```text
                    API Gateway
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
      Core            Tasks Service    CRM Service
                         │                 │
                       Go/Python        Go/Python
```

При этом остальная платформа не должна переписываться.

Поэтому необходимо:

* не использовать прямой доступ одного модуля к внутренним моделям другого;
* использовать service interfaces;
* использовать события;
* использовать стабильные API-контракты;
* хранить данные в обычной реляционной БД;
* минимизировать зависимость от конкретного языка.

## 6. Технологический стек

### Backend

Python + FastAPI.

Причины:

* высокая скорость разработки;
* хороший REST API;
* type hints;
* Pydantic;
* большое количество библиотек;
* удобная интеграция с AI в будущем;
* достаточная производительность для целевой аудитории.

Фактический состав — намеренно короткий. Кроме веб-фреймворка, драйвера БД и
инструментов паролей/токенов в нём есть ровно одна предметная библиотека:

```text
phonenumbers    # нормализация и проверка телефонов (раздел 9.1)
```

Это метаданные, а не сервис: ни сети, ни проверки номера где-то, ни отправки
SMS. Зависимость добавлена потому, что своя маска по длине была неверна для
всех стран, кроме нескольких — формат номера задаёт страна, а не длина.
Правило для дальнейших библиотек то же: **своя реализация формата дешевле,
пока она не становится неверной**.

### Frontend

React + TypeScript.

Frontend должен быть отдельным приложением.

```text
frontend/
backend/
```

Frontend собирается на этапе разработки/CI.

Production-сервер не должен компилировать frontend.

Зависимостей ровно три: `react`, `react-dom`, `react-router-dom`, плюс одна
предметная:

```text
libphonenumber-js    # та же таблица телефонов, что и на сервере (раздел 9.1)
```

Одинаковые метаданные на обеих сторонах — не совпадение: если фронтенд считает
маску по своим правилам, а сервер проверяет по чужим, то расхождение
показывается пользователю как «я ввёл правильно, а меня не пускают».

### Database

PostgreSQL.

Используется для:

* пользователей;
* организаций;
* проектов;
* задач;
* настроек;
* прав;
* модулей;
* событий;
* остальных данных платформы.

Миграции — Alembic.

### Reverse Proxy

Caddy.

Основные задачи:

* HTTPS;
* reverse proxy;
* отдача frontend;
* маршрутизация API.

Nginx может быть альтернативой, но для MVP предпочтителен Caddy.

### Docker

Docker Compose используется для deployment.

Первоначальный состав:

```text
docker-compose.yml

services:
  app
  postgres
  caddy
```

## 8. Core

Core — фундаментальная часть системы.

Core не должен содержать бизнес-логику конкретных прикладных областей.

### 8.1. Core содержит

Каталоги `core/` соответствуют коду, а не идее: то, чего в Core нет, не
должно и появиться «на будущее».

```text
core/
├── auth/            # пароли, токены, зависимости аутентификации
├── users/           # аккаунты, телефоны, видимость, присутствие
├── organizations/   # организации, участники, команды, оргструктура, список людей
├── projects/        # проекты
├── permissions/     # роли, ранги, каталог прав
├── files/           # файловое хранилище и квоты
├── activity/        # универсальная проекция событий
├── settings/        # настройки организации и личные настройки
├── events/          # Event Bus
├── modules/         # Module Registry
├── router.py        # сборка всех роутеров ядра
├── errors.py        # доменные исключения
├── pagination.py
├── dependencies.py
├── logging.py
└── exception_handlers.py
```

Команды (`teams`) живут в `organizations/`, а не отдельным каталогом: команда
существует только внутри организации и без неё не имеет смысла. Уведомлений в
ядре пока нет — они приходят своим этапом (roadmap, этап 5), и место под них
держит Event Bus, а не пустой каталог.

## 9. User

Пользователь системы.

Поля `users`:

```text
User
├── id
├── email
├── username
├── password_hash
├── first_name
├── last_name
├── avatar_file_id      # файл в FileService, не путь на диске
├── status              # active / invited / disabled
├── is_superuser
├── birthday            # nullable: год не обязателен
├── last_login_at       # когда последний раз доказал пароль
├── last_seen           # когда был здесь в последний раз (2.9)
├── created_at
└── updated_at
```

Три решения, которые стоит проговорить, потому что они неочевидны:

* **`last_login_at` и `last_seen` — разные вещи.** Первый отвечает на вопрос
  «когда человек последний раз вводил пароль», второй — «когда он был здесь».
  Человек, проработавший полдня без повторного входа, во втором случае здесь,
  а в первом — нет.
* **`birthday` nullable целиком, а не «год по умолчанию».** «Я не говорил» не
  должно читаться как «1970 год».
* **Настройки человека лежат не здесь, а в `user_settings`** (ключ/значение на
  пару «организация + человек»). Столбец в `users` означал бы, что у человека
  есть одна настройка на всю установку, а они разные в разных организациях.

Телефона в `users` нет: их несколько, у каждого свой тип и своя страна, поэтому
это отдельная таблица `user_phones` (раздел 9.1).

### 9.1. Телефоны человека

```text
UserPhone
├── id
├── user_id
├── number        # E.164: +79001234567
├── country       # ISO 3166-1 alpha-2, nullable
├── kind          # work / home / mobile / other
├── created_at
└── updated_at
```

Три правила, каждое из которых стоит отдельной миграции:

* **E.164 и только он.** Хранить «+7 (900) 123-45-67» значит сортировать по
  пунктуации и не находить по номеру, скопированному из счёта. Страна рядом —
  потому что без неё номер нельзя прочитать в национальном формате, а угадывать
  нельзя: чужой номер в чужом формате хуже, чем номер без формата.
* **Уникальность `(user_id, number)` в базе, а не только в сервисе.** «Рабочий»
  и «Мобильный» для одних цифр — это не два номера, а один, названный дважды.
* **Тип — закрытый список, а не строка.** Список придуман на этапе 2.8 и
  хранится enum'ом, потому что свободный текст приходилось бы угадывать при
  чтении.

### 9.2. Настройки организации и человека

Два реестра ключей, и разница между ними — не в реализации, а в том, кто ими
владеет:

| | Ключи | Владелец | Право на запись |
| --- | --- | --- | --- |
| `organization_settings` | `locale`, `timezone`, `date_format`, `week_starts_on`, `task_auto_archive_days`, `max_file_size_bytes`, `storage_quota_bytes`, `contacts_visibility`, `contacts_self_service`, `last_seen_visibility`, `last_seen_self_service` | установка | `organization.settings.manage` |
| `user_settings` | `locale`, `theme`, `date_format`, `people_info`, `contacts_visibility`, `last_seen_visibility` | человек | членство в организации |

Оба хранятся как `organization_id + key → value`, вторые — ещё и с `user_id`,
с уникальным индексом на тройку.

Значение `null` для личного ключа означает «у меня нет мнения», и строка при этом
удаляется: без этого выбрать настройку один раз означало бы выбрать её навсегда,
и порталное значение больше никогда не проступало бы.

### 9.3. Кто что видит о человеке

Видимость — это не право, а **личная настройка, которую портал может
разрешить или запретить**. Право отвечает на вопрос «кому вообще можно», настройка
— на вопрос «а что из этого этот человек готов показывать».

Оба вопроса (контакты и присутствие) решаются одним классом `Visibility` в
`core/users/visibility.py`, потому что это один и тот же вопрос, заданный дважды:

```text
portal.<field>_visibility      # для тех, кто не выбрал сам
portal.<field>_self_service    # могут ли вообще выбирать
stored.<field>_visibility      # ответ самого человека
```

Порядок ответа: **своё видно всегда**, **администратору всегда**, остальным —
если эффективное значение `everyone`. И при выключенном `<field>_self_service`
личное значение **отклоняется на записи** (`403`), а не игнорируется при чтении.

В будущем могут появиться:

* SSO;
* LDAP;
* OAuth;
* 2FA (roadmap 2.19);
* внешний identity provider.

На MVP достаточно стандартной авторизации.

## 10. Organization

Организация является верхним уровнем изоляции данных.

```text
Organization
├── id
├── name
├── slug
├── description
├── created_at
└── updated_at
```

### 10.1. Сколько организаций живёт на установке

**Ровно одна, и это решение, а не ограничение.**

Установка по умолчанию работает в режиме одной организации
(`SINGLE_ORGANIZATION=true`): организацию создаёт портал-администратор, а вторая
отклоняется с 409. Причина простая — у портала нет задачи изобретать управление
арендами раньше, чем это понадобится, а логика мультиарендности при этом никуда
не девается (раздел 10.2).

Множественность аккаунтов и членства в модели остаётся: один человек может
состоять в нескольких организациях, и это выражение через
`organization_members` работает при любом режиме.

### 10.2. Мультиарендность как функция масштабирования

Второй режим — **не отладочный**, а путь, по которому пойдёт установка, которой
понадобится больше одной организации. Поэтому он держится двумя правилами, а не
намерением:

**1. Граница проверяется тестами, а не обещаниями.** Тестовый набор работает с
выключенным `SINGLE_ORGANIZATION` (это делает `backend/tests/conftest.py`), а
`tests/test_single_organization.py` включает флаг обратно и закрепляет
поставляемую политику. Ровно одна организация на установке и множество
организаций в тестах — это не противоречие, а две половины одного обещания:
**форма, которую мы отгружаем, проверяется, и форма, под которую мы
масштабируемся, тоже проверяется.**

Вся проверка границы собрана в `backend/tests/test_tenant_isolation.py`: маршрут,
который отдаёт чужие данные, проверяется на **двух** организациях с читателем в
каждой. Граница, которую проверяют только с одной стороны, не проверена.

**2. Проверяется адресат, а не только читатель.** Маршрут с идентификатором в
пути должен спрашивать «этот человек — член **моей** организации?», а не
«читатель имеет право смотреть?». На одной организации разница не видна — все
одни и те же люди. Видно она становится только при установке вдвое.

Что аудит 2.23 нашёл именно здесь: `GET /users/{id}` и `GET /users/{id}/profile`
проверяли читателя и брали адресата по одному `id` — то есть на второй
организации отдавали её карточку целиком. Обе двери закрыты, закрытая дверь
закреплена тестом.

**Что это не значит.** Одна организация на установке — не запрет на вторую: флаг
переключается, модель данных и API для этого уже написаны. Это значит, что
переход — вопрос настройки, а не переделки, и что граница к этому моменту
проверяется тестами, а не держится на внимании автора.

Система должна сохранять историю значимых изменений.

Например:

```text
Max created task "Prepare report"

Max assigned task to Ivan

Ivan changed status:
TODO → IN_PROGRESS

Ivan changed priority:
MEDIUM → HIGH
```

Activity должна быть универсальной.

Core не должен знать, что событие произошло именно в Tasks.

## 21. Зачем нужен Event Bus

Он создаёт основу для будущей автоматизации.

Например:

```text
TaskCompleted
      │
      ├── Activity
      ├── Notification
      └── Automation
```

Позже:

```text
DealStageChanged
      │
      ▼
Automation Engine
      │
      ├── Condition
      ├── Create Task
      ├── Send message
      └── Notification
```

Таким образом, Automation не придётся встраивать непосредственно в Tasks или CRM.

## 22. Module Registry

Платформа должна иметь механизм регистрации модулей.

Каждый модуль должен иметь manifest.

**Эта секция — документация по модулям и обязательный порядок разработки:
любая разработка модуля ведётся в соответствии с ней.** Изменения самих
конвенций — только вместе с изменением документации.

### Место в структуре проекта

Модуль занимает отдельное, предсказуемое место с обеих сторон:

```text
backend/app/modules/<module_id>/
frontend/src/modules/<module_id>/
```

*Backend* — ровно один каталог на модуль:

```text
backend/app/modules/tasks/
├── manifest.py        # id, версия, права, маршруты, события, настройки, поля
├── models.py
├── repository.py
├── service.py
├── schemas.py
├── api.py
└── migrations/        # миграции модуля (общая цепочка Alembic)
```

*Frontend* — страницы, компоненты и API-клиент модуля; в ядро модуль
встраивается роутом и пунктом навигации, не правит существующие компоненты.

Требование лёгкого встраивания: подключение модуля — это (а) каталог
модуля, (б) строка в `ENABLED_MODULES`, (в) роут/раздел на фронте.
Core не должен содержать предметной логики модуля (см. §64).

### Manifest

Manifest содержит:

```text
id              # стабильный идентификатор (имя каталога)
name
version
description
dependencies    # другие модули, от которых зависит
permissions     # полный набор прав модуля, namespace "<module_id>.*"
routes          # HTTP-маршруты
events          # подписки/публикации в Event Bus
settings        # ключи настроек модуля (реестр, раздел в настройках)
fields          # стандартные поля, которые модуль заводит (см. ниже)
```

### Стандартные поля

Каждый модуль при добавлении заводит стандартные поля, соответствующие
ему (например, для Scrum — `epic`, `story_point`). Правила:

* имена полей — фиксированные, в `snake_case`, утверждаются в реестре
  стандартных полей (раздел `fields` manifest);
* если поле повторяется в нескольких модулях, оно называется одинаково и
  заводится **одним** определением, а не копиями на каждый модуль;
* реализация — на общем движке пользовательских полей, заведение
  определений — миграцией модуля, не правкой ядра.

### Права модуля

Каждый модуль создаёт свой набор прав (namespace `<module_id>.*`) и
объявляет их в manifest. При включении модуля эти права появляются в
соответствующем разделе настроек и назначаются через группы прав — без
правки кода ядра (см. также §25, цель — убрать захардкоженные grant'ы).

### Чек-лист разработки модуля

1. Каталог создан по структуре выше (backend + frontend).
2. Manifest заполнен: права, маршруты, события, настройки, поля.
3. Стандартные поля заведены реестром, одинаковые имена — не переименовывать.
4. Права в настройках, выдача — через группы, ядро не правилось (кроме
   `ENABLED_MODULES`).
5. Миграции — в общей цепочке Alembic, `alembic check` чистый.
6. Проверки зелёные: `ruff`, `mypy --strict`, `pytest`, `tsc`,
   `npm run build`; изменение API — e2e на чистой БД.
7. Документация (эта секция + docs/architecture.md) обновлена вместе с
   модулем.

## 23. Module Manager

Module Manager отвечает за:

* обнаружение модулей;
* проверку зависимостей;
* регистрацию маршрутов;
* регистрацию permissions;
* регистрацию событий;
* регистрацию UI;
* управление состоянием модуля.

На первом этапе модули физически поставляются вместе с платформой.

То есть:

```text
Modules
├── Tasks      enabled
├── Kanban     disabled / not installed
├── CRM        not installed
└── Chat       not installed
```

### Установка модулей

Три поддерживаемых способа получить модуль:

1. **Вручную** — каталог модуля добавлен в репозиторий/образ и включается
   через `ENABLED_MODULES`. Базовый способ, работает всегда.
2. **С основного репозитория платформы** — установка из каталога
   (реестра) официальных модулей того же проекта.
3. **С другого репозитория по ссылке** — git-URL внешнего репозитория.

Для способов 2 и 3 действуют:

* источники доверия (allowlist разрешённых репозиториев — настройка
  портала, меняет только администратор);
* установка только явным действием администратора, никогда автоматически;
* фиксация установленной версии/коммита в журнале установленных модулей;
* после установки — миграции модуля и включение флагом; выключение —
  без остатков в ядре.

Каталог модулей в среде:

```text
Modules
├── Tasks      installed: bundled    enabled
├── Chat       installed: main repo  enabled
└── Scrum      installed: <url>      disabled
```

## 24. Важное ограничение MVP

На первом этапе **не реализовывать полноценную систему установки сторонних plugins**.

Не делать сразу:

* marketplace;
* загрузку ZIP;
* dependency resolver;
* подпись plugins;
* sandbox;
* удалённую установку.

Сначала должна заработать сама модульная архитектура.

Установка модулей с основного репозитория и по ссылке (§23) — не MVP, а
отдельный этап платформы модулей в roadmap; она остаётся без marketplace,
ZIP-загрузки, dependency resolver и sandbox — только явная установка
администратором из источника из allowlist.

## 25. Permissions

Минимальная система прав существует уже в MVP, и она каталогизирована: каждая
строка права живёт либо в `core/permissions/registry.py` (ядро), либо в
`manifest.py` модуля. Каталог — это объединение обоих, поэтому проверке права
не нужно знать, кто его объявил.

Каталог ядра:

```text
user.view
user.update

organization.view
organization.create
organization.update
organization.delete
organization.members.manage
organization.settings.manage

team.view
team.create
team.update
team.delete
team.members.manage

orgstructure.view
orgstructure.manage

project.view
project.create
project.update
project.delete

activity.view
```

Модуль `tasks` добавляет свои:

```text
task.view
task.create
task.update
task.delete
task.assign
task.complete
comment.create
comment.delete
```

Права — это строки с namespace, а не флаги. Разрезание по смыслу важнее, чем
по удобству, и в каталоге это видно по одной паре: `orgstructure.view` есть у
каждого, потому что посмотреть, кому кто подчиняется, — это не
административное действие, а `orgstructure.manage` остаётся у админов, потому
что перерисовать структуру — да. По той же причине `task.assign` есть у member,
а `task.delete` — нет: назначить задачу можно тому, кто её делает, удалить —
нет.

### 25.1. Роли

Роли заданы в коде, а не настраиваются: четыре предопределённых набора, потому
что сам факт «кто может менять права» — тоже право, и если роли редактируются,
то это право требует суперпользователя.

```text
owner  — всё, включая будущие права модулей (wildcard *)
admin  — управление организацией, структурой и удаление
member — работа: задачи, комментарии, команды
viewer — только чтение
```

Правило ранга: **менять роль может только строго более старший**. Админ не
трогает админа и тем более владельца, последнего владельца нельзя разжаловать,
а понизить себя можно только вниз — повышение было бы эскалацией привилегий.

В дальнейшем можно добавить:

```text
project roles
custom roles
permission groups   # roadmap, этап 4
```

## 27. Backend structure

Структура соответствует коду:

```text
backend/
├── app/
│   ├── main.py                # create_app, lifespan, bootstrap модулей
│   ├── api/                   # health, system (вне core: не домен)
│   ├── config/                # настройки из окружения, генерация ключа
│   ├── core/                  # фундамент платформы (см. §8.1)
│   ├── database/              # engine, session, Base
│   └── modules/
│       └── tasks/
│           ├── manifest.py    # контракт модуля (см. §22)
│           ├── permissions.py # строки прав модуля
│           ├── models.py
│           ├── repository.py
│           ├── service.py
│           ├── schemas.py
│           ├── events.py      # публикуемые события
│           ├── api.py
│           └── schemas.py
│
├── alembic/versions/          # единая цепочка миграций
├── tests/
├── Dockerfile
└── requirements.txt
```

Внутри `core/<feature>/` порядок слоёв обязателен:

```text
models.py → schemas.py → repository.py → service.py → api.py
```

* **repository** знает только про БД и ничего — про права и про события;
* **service** содержит правила и публикует доменные события;
* **api** не обращается к БД напрямую: роутер только разбирает запрос, зовёт
  сервис и переводит доменное исключение в HTTP.

Проверка правится в одном месте — на границе сервиса и БД, а не в каждом
роутере, потому что «забытый чек» в одном роутере из двадцати — это дыра,
которую не найдёт чтение кода.

## 28. Frontend structure

```text
frontend/
├── src/
│   ├── app/               # роуты, страницы, единственный CSS-файл
│   │   ├── App.tsx
│   │   ├── pages/
│   │   └── styles.css
│   ├── core/              # то, чем пользуются и модули
│   │   ├── api/           # клиент (fetch, ошибки домена)
│   │   ├── auth/
│   │   ├── users/         # люди: список, профиль, телефоны, присутствие
│   │   ├── organizations/ # организации, оргструктура, picker людей
│   │   ├── projects/
│   │   ├── settings/      # личные настройки
│   │   ├── permissions/   # capabilities, зеркало прав
│   │   ├── ui/            # Listbox, DateField, Popover, колонки
│   │   ├── layout/
│   │   ├── i18n/          # en/ru, контекст
│   │   ├── theme/
│   │   ├── hooks/
│   │   └── format.ts
│   └── modules/
│       └── tasks/         # страницы, компоненты, api, типы модуля
│
├── package.json
└── Dockerfile
```

Правила, которые ядро держит для себя:

* **`core/ui/` не знает о домене.** `Popover`, `Listbox`, `ColumnSettings` — это
  механики; одна механика, один экземпляр. Настройка столбцов сегодня работает
  и в задачах, и в списке людей, и это дешевле, чем две копии.
* **`core/` не импортирует `modules/`.** Обратное — можно и нужно.
* **Правила видности не пересчитываются на интерфейсе.** Сервер присылает
  готовый флаг, и экран его показывает или не показывает; интерфейс не решает,
  можно ли человеку видеть телефон.
* **Своей таблицы переводов нет.** Словарь живёт в `core/i18n`, ключи обязаны
  существовать в `en.ts` и `ru.ts` одновременно — это проверяется, а не
  договаривается.


И две оговорки, которые видны только в процессе:

* **Никакого inline-редактирования в списках.** Список остаётся списком: в
  строке — ссылка на человека, всё остальное правится в его карточке.
  Экономия одного клика не стоит режима правки, который живёт в двух местах.
* **Настройка столбцов — всплывающая панель, а не блок в потоке.** В потоке она
  сдвигала таблицу вниз, и человек, открывший её посмотреть порядок столбцов,
  терял из виду тот самый порядок.

## 43. Files

На первом этапе файловое хранилище локальное, и оно уже реализовано: каталог на
постоянном volume, квоты (на человека и на подразделение), загрузка, выдача и
удаление через один `FileService`.

В дальнейшем:

```text
Local Storage
S3
MinIO
Cloud Storage
```

За этим должна скрываться реализация хранилища, и модули не должны работать с
filesystem/S3 напрямую.

Три решения, которые уже приняты и не должны ломаться:

* **Файлы принадлежат организации.** Чужой файл нельзя получить, зная его id, и
  проверка живёт на отдаче, а не на выдаче ссылки.
* **Аватар — это файл, а не отдельная колонка с путём.** Имя файла служит
  ключом кэша: новая картинка — новое имя, поэтому браузер не показывает старую
  после загрузки.
* **Квота проверяется на записи**, а не при чтении: превышение обнаруживается
  на загрузке, где ещё можно отказать, а не после того, как файл уже занял
  место.

## 44. Security

Минимальные требования:

* password hashing (argon2);
* authentication;
* authorization;
* HTTPS;
* input validation;
* SQL injection protection через ORM/query layer;
* CORS configuration;
* secure cookies/token handling;
* rate limiting — позже;
* audit log — через Activity.

Пароли никогда не хранятся в открытом виде.

Требования, которые добавились по ходу и которые стоит называть отдельно,
потому что они не про «не пускать постороннего», а про «не отдавать лишнее
своему»:

* **Изоляция организаций — на уровне запроса.** `organization_id` обязателен в
  path и присутствует в каждой таблице проектов, команд, структуры и активности;
  маршрут без него физически не может быть авторизован, потому что право берётся
  из пути, а не угадывается.
* **Правила ранга при изменении ролей.** Админ не трогает админа и владельца,
  последнего владельца нельзя разжаловать, себя можно понизить только вниз.
* **Межтенантные чтения закрыты.** `GET /users` — только суперпользователь
  (раздел 26).
* **Человек скрывает то, что о нём, сам** (раздел 9.3), и сервер скрывает это
  и в профиле, и в списке людей, и вместе с фактом, что адрес скрыт.
* **Телефон нормализуется и проверяется на сервере** (раздел 9.1): в базу не
  попадает то, что не является номером, а дубликат невозможен на уровне схемы.
* **Секрет JWT генерируется при первом старте** и лежит на постоянном volume, а
  в репозитории нет общеизвестного ключа. Секрет из окружения имеет приориент —
  он нужен, если ключ хранится в secret manager или его должны разделять
  несколько инстансов.

## 45. Testing

Минимальный набор:

```text
Unit tests
Integration tests
API tests
```

Для MVP обязательно протестировать:

* регистрацию;
* login;
* создание организации;
* создание проекта;
* создание задачи;
* изменение задачи;
* назначение задачи;
* изменение статуса;
* комментарии;
* permissions.

Тесты идут против **настоящего PostgreSQL**, а не против SQLite: в схеме есть
JSONB, нативные UUID и enum с CHECK-constraint, и подмена движка убрала бы ровно
то, что ломается в бою. Фикстура применяет настоящие миграции Alembic, поэтому
сломанная миграция валит тесты, а не production.

Сверх этого обязательно покрыты места, где ошибка не бросает исключение, а
просто отдаёт неверный ответ:

* видимость контактов и присутствия — включая все отказы (раздел 9.3);
* правила записи присутствия и троттлинг;
* телефоны: нормализация, страна, отказ невозможному номеру, запрет дубля;
* админ-редактор участника: что меняется, что не меняется и кто не может;
* межтенантные границы: список людей, чужие организации, чужие файлы.

У фронтенда **нет раннера тестов**, и это сознательное решение на текущем
этапе: проверяются `tsc`, сборка и поведение через API, а то, что нельзя
проверить без браузера (маска номера, порядок хуков, попап), описано рядом с
кодом. Когда раннер появится, первыми кандидатами должны быть именно эти места.
