# План следующей итерации (roadmap)

Источник: личные наброски от 07.10.2026 (даты и ФИО вычищены). Дубли из разных
сообщений (статусы, лента) сведены в один пункт соответствующего этапа.

## Как читать

- Этапы пронумерованы 1–8, задачи внутри — N.M. Порядок этапов обоснован
  зависимостями (см. ниже), внутри этапа порядок задач тоже смысловой.
- Статус — первая строка под заголовком этапа и задачи: 🟢 выполнен,
  🟡 в процессе, 🔴 не начато (цвет в markdown передаётся эмодзи). Статус
  обновляется по мере работы; правила оформления — в конце документа.
- Блоки **Вопросы** / **Риски** / **Улучшения** есть только там, где они есть.
  Вопросы без ответа блокируют только свою задачу, пока не отмечено иное;
  сводка блокирующих — в конце документа.
- Каждый шаг закрывается зелёными проверками: `ruff`, `mypy --strict`, `pytest`,
  `tsc`, `npm run build`; при изменении API/миграций — e2e на чистой БД; новые
  ключи i18n — парой в `en.ts`/`ru.ts`; схема — только миграциями.
- Модульность: всё, что является отдельной продуктовой областью (чаты, статусы,
  лента), делается модулем по паттерну `manifest.py` (permissions, events,
  routes) — как `backend/app/modules/tasks`. Ядро не обрастает предметной
  логикой; модуль подключается строкой в `ENABLED_MODULES` и не правит ядро,
  кроме каталога прав (см. задачу 4.7, цель — убрать и это дублирование).

## Порядок этапов и обоснование

1. **Дизайн-система** — первым, чтобы не перекрашивать новые экраны дважды.
2. **Пользователи** — аватары, профили, присутствие нужны спискам, комментариям
   и чату; инфраструктура загрузки файлов (раз) нужна и чату (после).
3. **Список задач и комментарии** — ядро продукта; серверные сохранённые фильтры
   делаются здесь, потому что шаринг фильтров (этап 4) требует серверной сущности.
4. **Права и группы прав** — раньше пользовательских полей (их видимость
   ссылается на группы) и раньше шаринга фильтров (нужно право `filter.manage`).
5. **Уведомления** — опирается на существующий in-process Event Bus; центр
   уведомлений нужен чату (системные уведомления), поэтому раньше чата. Здесь
   же появляется серверный пуш (SSE), без которого браузерные уведомления о
   комментариях (пункт из списка задач) бессмысленны.
6. **Пользовательские поля и группировка** — после прав (видимость полей) и
   после готовности списка (колонки, карта поведения, массовое редактирование).
7. **Чаты** — крупнейший модуль; требует аватаров, файлов, уведомлений, прав и
   SSE — всё это к этому моменту готово.
8. **Обновление ПО** — независимо от продуктовых этапов, зависит только от
   среды развёртывания; можно делать в любой момент после ответа на вопрос 8.0.

Частично этапы параллельны (8 не пересекается с 1–7; 2 и 3 слабо пересекаются),
но внутри этапа порядок сохранять.

## Этап 1. Дизайн-система, тема и компоновка

**Статус:** 🟡 в процессе

Цель: единая тема, воздух между элементами, компонент списка вместо нативного,
навигация без хлебных крошек.

### 1.1 Токены темы и переключатель

**Статус:** 🟢 выполнен

Перевести оформление на CSS custom properties (примитивы → семантические токены:
фон, поверхность, текст, акцент, граница, состояния). Основная тема — жёлтый
(золотистый) с чёрным, синяя — альтернатива, переключатель в профиле (где сейчас
переключатель языка). Хранение — localStorage, как язык.

**Результат:**

- Цвета разведены по блокам `data-theme` на `<html>`: золотая тёмная по
  умолчанию (`[data-theme='gold']`, акцент `#F8C840` с референса, чёрный текст
  на акценте, `color-scheme: dark`), синяя — текущая «как есть» (светлая +
  системная тёмная; медиа-запрос стал `:root:not([data-theme='gold'])`).
- Переключатель — селект «Тема» в профиле рядом с языком; ключ
  `tasktracker.theme` в localStorage; первая отрисовка — инлайн-скриптом в
  `index.html` до загрузки стилей (без вспышки не-золотой темы).
- Форма (по ref1/ref2, «нравится форма панелей и кнопок»): радиусы подняты до
  6/8/16px (контролы/строки/панели) — три числа в `:root`, правка одной
  строкой, если форма на осмотре не та.
- Решения по вопросам: палитра — только тёмная золотая; синяя тема — оставить
  как есть; переключатель — только в профиле.

- Вопросы:
  - Точная палитра: дать референс/оттенки или согласовать моё предложение
    (чёрный текст на жёлтом акценте — добиться контраста AA)?
  - Синяя тема — оставить текущую визуальную версию «как есть»?
  - Переключатель темы: в профиле достаточно или нужен ещё в шапке?
- Риски:
  - Жёлтый как фон больших площадей с белым текстом ломает контраст —
    жёлтый только как акцент, текст на нём чёрный; проверить focus/error/hover.
- Улучшения:
  - Тема по `data-theme` на `<html>` — позже переносится в серверные
    настройки без переделки.

## Этап 2. Пользователи, профили и персональные настройки

**Статус:** 🔴 не начато

Цель: файловое хранилище, аватары сквозными, профили участников, присутствие,
персональный экран настроек (на нём будут расти разделы последующих этапов),
оргструктура (карточка отдела, popup, должности) и единый список сотрудников.

### 2.1 Персональные настройки: хранилище и экран

**Статус:** 🔴 не начато

Таблица `user_settings` (org, user, key, value JSONB) по образцу
`organization_settings` + реестр ключей (как `SETTING_DEFINITIONS`). Экран
персональных настроек с секциями; смена языка и темы живут в нём (хранение
v1 — localStorage, см. 1.1; серверный перенос — улучшение, когда настройки
станут «значимыми»).

- Вопросы:
  - Маршрут: `/settings` занят настройками организации — предлагаю
    `/preferences`. Подходит?
- Риски:
  - Реестр ключей сейчас жёсткий только для организации; для модулей,
    объявляющих свои настройки (чат, статусы), заложить механизм
    регистрации ключа из manifest — иначе реестр станет мусорной свалкой.

### 2.2 Инфраструктура загрузки файлов

**Статус:** 🔴 не начато

Общий сервис файлов: multipart-загрузка, лимит размера, whitelist MIME,
таблица `files` (организация, владелец, размер, тип), постоянный volume
(`/var/lib/tasktracker/uploads`), отдача через API с проверкой членства
в организации (не публичный статик).

- Вопросы:
  - Локальный volume (предлагаю сейчас, за абстракцией интерфейса — потом S3)
    или сразу S3-совместимое хранилище?
  - Обработка изображений: клиентский даунскейл/кроп перед загрузкой
    (без новых зависимостей, предлагаю) или Pillow на сервере (миниатюры
    делает сервер)?
  - Максимальный размер файла (аватар — 2–5 МБ?) и общая квота на файлы.
- Риски:
  - Квоты на диск — иначе файлы заполнят volume; soft-лимит + счётчик в БД.
  - Обход проверок при отдаче — единая точка отдачи файлов, путь к файлу
    только из id в БД, никакой конкатенации из запроса.

виден меньше 5 минут. Отображение: профиль, списки участников (при

- Вопросы:

- Риски:

## Этап 6. Пользовательские поля и группировка

**Статус:** 🔴 не начато

Цель: типизированные пользовательские поля задач с параметрами и видимостью,
интеграция со списком (колонки, карта поведения, массовое редактирование,
фильтры/сортировка) и группировка списка.

### 6.1 Размещение engine (ADR — до кода)

**Статус:** 🔴 не начато

Таблицы с `entity_type` (v1 = `task`) и сервис в модуле `tasks`; контракт
описать в docs/architecture.md — при втором потребителе (чаты, анкеты)
поднять в core без смены API.

- Вопросы:
  - Согласны на «внутри tasks, но с entity_type»? (предлагаю да.)

### 6.2 Определения полей

**Статус:** 🔴 не начато

Таблица `custom_field_definitions` (организация, entity_type, key, label,
тип, params JSONB, порядок, visibility) + CRUD API + UI в настройках задач.
Право: свой ключ `task.fields.manage` (кому выдавать по умолчанию — вопрос).

- Вопросы:
  - Кто управляет полями: администратор организации? владелец? (предлагаю:
    владелец + админ.)

### 6.3 Типы полей v1

**Статус:** 🔴 не начато

Строка; целое; число; дата; дата и время; пользователь; другая задача;
ссылка; проект; отдел. Для каждого — контрол ввода, валидация типа,
отображение в карточке (ссылочные типы — как ссылка на сущность).

- Риски:
  - Ссылочные типы (задача/проект/отдел) — удаление сущности не должно
    оставлять битых значений: ON DELETE SET NULL + отображение «(удалено)».

### 6.4 Параметры: множественное, обязательное, скрытое от

**Статус:** 🔴 не начато

- «Множественное»: массив значений (отдельные строки в таблице значений).
- «Обязательное»: см. вопрос о моментах проверки.
- «Скрытое от»: списки подразделений, групп прав, конкретных пользователей;
  хранение — JSONB-правила на определении, вычисление «видит ли пользователь»
  одним запросом.

- Вопросы:
  - Когда проверять «обязательное»: при создании задачи, при любом
    сохранении, или только перед завершением? (предлагаю: при создании и
    перед завершением — не блокировать черновики.)

### 6.5 Хранение значений

**Статус:** 🔴 не начато

Таблица `custom_field_values`: определение + задача + типизированные колонки
значения (текст, число, дата, ссылочный id) под индексы
`(definition_id, value)`. Не jsonb-колонка в tasks: слабые индексы и ALTER
таблицы задач на каждое поле.

- Риски:
  - Фильтрация/сортировка — JOIN; ограничить число одновременно
    фильтруемых полей на запрос (защита от квадратичных планов).
  - Рендер карточки со 100 полями — batch-load значений одним запросом
    (никаких N+1).

### 6.6 Видимость: закрыть все пути чтения (главный риск этапа)

**Статус:** 🔴 не начато

Значение поля, скрытого от пользователя, не должно утекать: карточка задачи,
список/колонки, поиск по задачам, сортировка, фильтрация, массовое
редактирование, прямые ссылки на задачу, активность/лента, подсказки/автодополнение.
Фильтрация на чтении (ответ отдаётся уже отфильтрованным) + тест на каждый путь.

- Вопросы:
  - Показывать ли сам факт существования скрытого поля («есть поле, но вам
    не показано») или не показывать ничего? (предлагаю: не показывать.)
- Риски:
  - Утечка через сортировку/фильтр (поле участвует в плане запроса, но значение
    не отдаётся — пользователь восстанавливает его бинарным поиском по
    сортировке) — скрытое поле нельзя использовать в сортировке/фильтре для
    тех, кому оно скрыто.

### 6.7 Интеграция со списком

**Статус:** 🔴 не начато

Пользовательские поля как опциональные колонки (настройки колонок) + правила
поведения из 3.7: дефолт для пользовательских полей — «ничего» (редактировать
можно из карточки/инлайн, если настроено).

- Вопросы:
  - Дефолт поведения для пользовательских полей: ничего / редактировать для
    одиночных? (предлагаю: ничего.)

### 6.8 Фильтрация и сортировка по пользовательским полям

**Статус:** 🔴 не начато

Расширить whitelist параметров `GET /tasks` (ключ поля → predicate по
join-значению), типизированные индексы из 6.5, тесты планов запросов на
большом объёме.

### 6.9 Группировка списка

**Статус:** 🔴 не начато

Разворачиваемые группы по значению любого поля (статус, проект, приоритет,
ответственный, срок, пользовательские) — настройка в панели фильтров,
состояние в URL.

- Вопросы (согласовать ДО кода — API зависит от ответа):
  - Группировка против пагинации: предлагаю — при включённой группировке
    пагинация отключается, но есть cap (например 2000 задач) с предупреждением
    «узкие фильтры». Альтернатива — серверная пагинация по группам (дороже и
    сложнее). Какой вариант?
- Риски:
  - Выбор варианта определяет контракт API — не начинать с кода до ответа.

### 6.10 Итог этапа

**Статус:** 🔴 не начато

Поля создаются админом, рендерятся, фильтруются, сортируются, скрытие

## Правила оформления документа

- **Статус** — первая строка под заголовком этапа и задачи:
  `**Статус:** 🟢 выполнен` / `**Статус:** 🟡 в процессе` /
  `**Статус:** 🔴 не начато`. Цвет в markdown передаётся эмодзи
  (`<span style>` не отображается, `<mark>` даёт только жёлтый).
  🟢 — сделано и проверки зелёные; 🟡 — начато, не закрыто; 🔴 — не начато.
  Статус этапа — производный от задач: пока есть 🔴/🟡, этап не может быть 🟢.
- **Нумерация**: этапы 1–8, задачи внутри этапа — N.M. Задачи текущей
  итерации встроены в этапы и стоят перед «Итог этапа» (1.8–1.9, 2.13–2.18);
  отдельного раздела-батча нет.
- **Блоки** *Вопросы* / *Риски* / *Улучшения* — только если они есть;
  вопрос без ответа блокирует свою задачу, сводка — в приложении A.
- **Проверки** после каждого блока: `ruff`, `mypy --strict`, `pytest`,
  `tsc`, `npm run build`; изменение API/миграций — e2e на чистой БД
  (после чистки — новые админ-креды); ключи i18n — парой в `en.ts`/`ru.ts`;
  схема — только миграциями.
- **Статусы обновлять по мере работы**: закрыл задачу — сразу 🟢;
  этап перестал быть полностью невыполненным — 🟡.
